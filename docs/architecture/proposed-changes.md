# Proposed changes: a workspace change Piloti proposes and a person applies

A **proposed change** is a change to the office's workspace that Piloti
proposes and a person applies. It is a server object with its own lifecycle,
not a card that executes itself (ADR-0105). Three kinds exist:

| Kind | What it proposes | The card |
|---|---|---|
| `file_operation` | move documents into a folder, rename them, create a folder, or assign a document to a colleague | `file_operation_proposal` |
| `memory` | a note for the office's memory, or for the project's | `memory_proposal` |
| `project_profile` | a change to the project's facts, goals, unknowns or assumptions, as a JSON patch on the profile | `project_profile_patch` |

All three share one lifecycle, one table, one set of routes and one receipt
card. What differs between them is held in one file,
`frontends/ui/src/lib/proposals/kinds.ts`: the payload schema, who may decide,
what is refused when it is proposed, the inbox line, and which applier runs.
The lifecycle in `service.ts` is the same for every kind and asks `kinds.ts`
for the rest.

Before, each card decided in the reader's browser and wrote the decision into
the chat message (`cardInteractions`): the file card ran its moves from the
browser, the memory card posted the note, the profile card posted the patch.
Nobody else saw the decision, nothing recorded what each item did, a second tab
could run the same moves again, and what Piloti read back was the card's own
preview. Now the card shows the server's object, the server applies it in the
deciding person's session, and the decision is one row every reader sees.

## The data

`proposed_changes` sits under `grid_secure_table` RLS: the organization, and the
project's organization. Both foreign keys are composite with the organization
(`projects (id, organization_id)`, `conversations (id, organization_id)`), so a
row cannot name another tenant's project or conversation.

| Column | Holds |
|---|---|
| `project_id` | the project the change is for. Always the turn's, taken from the signed envelope |
| `kind`, `payload` | one of the three kinds and its payload, below |
| `status` | `proposed`, `applied`, `partially_applied`, `failed`, `dismissed` |
| `proposed_by_kind`, `on_behalf_of` | `piloti` today, and the person whose turn proposed it |
| `origin_conversation_id`, `origin_message_id` | where the card sits. The proposal goes when its conversation goes |
| `origin_card_index` | which card of that answer made it. With `origin_message_id` it is the idempotency key, below |
| `decided_by`, `decided_at` | who applied or dismissed it, and when |
| `results` | one `{ label, ok, reason?, itemId?, scope? }` per item, in order. `itemId` is the id of what the apply created, when it created something addressable (a memory note); `scope` (`project` or `organization`) is the memory that note went into, which is the decider's choice and not always the payload's. A row decided before it was recorded has none |
| `applying_by`, `applying_since` | the claim of an apply in progress. Not part of the contract |

The CHECKs hold the lifecycle, so no code path can break it:

- A proposal has `decided_by` and `decided_at` exactly when it has left
  `proposed`.
- It has `results` exactly when it was applied (`applied`, `partially_applied`,
  `failed`), and `results` is an array.
- The claim has both columns or neither, and exists only while the proposal is
  `proposed`.
- `kind` is `file_operation`, `memory` or `project_profile`; `status` and
  `proposed_by_kind` are known values; `payload` is an object.
- `origin_card_index` is null or not negative, and needs an `origin_message_id`
  (a card index names a card of one answer).

`scripts/rls-test-db.sh` refuses each CHECK and each cross-tenant foreign key
against a real PostgreSQL, applies the down migrations, and re-applies the up
migrations twice. `src/lib/proposals/repository.integration.spec.ts` runs the
repository as `grid_app_rw`. The down migration of 0143 is lossy: it deletes the
proposals of the two newer kinds, which the older build cannot read (their cards
fall back to deciding in the browser), and forgets which card made which
proposal.

## The three kinds

### `file_operation`

Payload (`fileOperationPayloadSchema`): `operation` (`move`, `rename`,
`create_folder`, `assign`), `operations` (one to eight items) and an optional
`note`. Documents are named by file NAME and folders by PATH, never by id: the
agent's inventory has no ids, and the deciding person's session resolves the
names when the change is applied. Every item must carry the fields its verb
needs, or the proposal is refused when it is made (422,
`proposal-item-incomplete`).

Gate: the documents' write, `project:documents:write` or `project:edit`
(`DOCUMENT_WRITE_PERMISSIONS`). Applier: `applyFileOperations`
(`executors.ts`), one result per item, described under [How apply runs](#how-apply-runs).

### `memory`

Payload (`memoryPayloadSchema`): `scope` (`project` or `organization`), `kind`
(the memory vocabulary: `decision`, `constraint`, `open_question`,
`derived_fact`, `preference`), `content` (up to 500 characters), `confidence`
and an optional `supersedes`, the earlier note this one corrects, quoted
verbatim. Accepting a correction retires the note it quotes
(`createProjectMemoryItem`'s `supersedesContent`).

Piloti proposes one only where it may not write the note itself: the `remember`
tool, when an organization-scoped write is refused by the deployment
(`GRID_ALLOW_AGENT_ORG_MEMORY` unset) and the turn is not restricted. So the
tool's proposals are organization-scoped today; `project` is in the contract
for the day a project note needs a person.

Gate: the project's memory write, `project:memory:write` or `project:edit`
(`MEMORY_WRITE_PERMISSIONS`, the same gate `addProjectMemoryItem` uses). An
organization note needs no more than that to decide, because any member writes
the office's memory, so the project's gate is the one that applies. The
decider's right to read the conversation comes first, as for every kind.

Applier: `applyMemory`. Before anything is written it runs the agent's own
memory door's checks, because a click is not a way around them:

1. `requireMayRememberFrom`: a conversation that drew on another project still
   restricting its readers (ADR-0094) remembers nothing (409,
   `CROSS_PROJECT_MEMORY`).
2. `requireResourceAccess(conversation, viewer)`, so a refusal says nothing
   about a conversation the decider cannot read.
3. `requireMayLeaveConversation(…, 'memory')`: a conversation that recorded a
   folder not every member may read (ADR-0087) is **confined**, and a note from
   it is refused (403). The check does not depend on the scope: the office's
   memory is read by every project, and a project's memory by every member of
   it, so neither may carry what a restricted folder said.

A refusal is thrown, not recorded as a failed result: the claim is given back
and the proposal stays `proposed`, for someone, or some time, it does not
refuse. Then it writes through the door a person's own click uses:
`addProjectMemoryItem` for the project, `createOrganizationMemoryItem` for the
office, with the conversation as `sourceConversationId` (purging a folder that
conversation drew on deletes the note with it). The result is one item, labelled
with the note's first twelve words, with the new note's id as `itemId` and the memory it went into as `scope`.

### `project_profile`

Payload (`projectProfilePayloadSchema`): `title`, an optional `rationale`, and
`patch`, one to twenty JSON-patch operations restricted to `/facts`, `/goals`,
`/unknowns` and `/assumptions`. The patch is what is applied and what the record
says was proposed; the title and rationale are what the reader is told. There
is no stored preview: the card's Feld / Vorher / Nachher rows are derived from
the patch against the profile as it is when the reader looks
(`buildPatchPreviewRows`). A value outside the intake vocabulary is refused
when it is proposed, not first when it is accepted (422,
`proposal-profile-vocabulary`).

Gate: `project:memory:write` or `project:edit`, the same two rights
`PROFILE_WRITE` in `profile-service.ts` asks. Applier: `applyProjectProfile`
calls `patchProjectProfile` with the proposal's conversation as origin, so the
profile's own confinement refusal (ADR-0087) applies and is thrown like the
memory one. An outcome that belongs to the proposal (the profile moved under it:
a version conflict; or a value the vocabulary refuses) is a failed result with
the service's reason, and the status is `failed`. One result for the whole
patch.

### Who may decide, per kind

| Kind | Right to decide (any of) | Written through |
|---|---|---|
| `file_operation` | `project:documents:write`, `project:edit` | the Files pane's services, per item |
| `memory` | `project:memory:write`, `project:edit` | `addProjectMemoryItem` or `createOrganizationMemoryItem` |
| `project_profile` | `project:memory:write`, `project:edit` | `patchProjectProfile` |

`DECIDE_PERMISSIONS` in `kinds.ts` holds the table. It is the applier's own
gate: a decider who passes it is not then refused by the service that writes.

## The lifecycle

```
proposed ──apply──▶ applied | partially_applied | failed
    │
    └──dismiss──▶ dismissed
```

1. **Piloti proposes.** A tool, or the end of the turn, calls
   `POST /api/internal/proposals` with the turn's signed envelope. The route
   pins the asker's session (ADR-0054 §4). The project and the conversation come
   from the envelope, and the body cannot name a project because its schema is
   strict. The asker needs `project:view`. Proposing changes nothing, so reading
   is enough. The route returns the id and the status, and the card carries the
   id as `proposal_id`.
2. **A person reads it.** `GET /api/proposals/[id]` returns the view with
   `canDecide`.
3. **A person decides.** They apply it or dismiss it. Both transitions are
   compare-and-swap on `proposed`, so a decision that is too late gets a 409.

### Where each kind is created

| Kind | Created by |
|---|---|
| `file_operation` | `propose_file_change`: one call, one card, one proposal |
| `memory` | `remember`, when an organization-scoped write is refused |
| `project_profile` | `register_envelope_card`, at the point the model's own `project_profile_patch` card becomes final. A turn that may not compose the card (a confined one) never gets there |

`add_card` in `proposals_client.py` registers the card first and asks for the
proposal second, so the index it sends is the position the card really has: a
tool running in parallel can add its own card while the request is out. When the
BFF answers, the card is replaced in place by a copy carrying `proposal_id`.

### One card, one proposal: the idempotency key

The create takes `answerMessageId` and `originCardIndex`. Together with the
organization they are a **unique index** (`uniq_proposed_changes_origin_card`,
partial: only rows with a card index), so one card of one answer is one
proposal however often the turn's finish runs. A second create for the same card
inserts nothing and returns the FIRST proposal as it stands, which means its id
and its current status, decided or not. It tells nobody again: the inbox item
is made once. A proposal made outside an answer needs no index and has none.

Only the request's OWN first proposal comes back. The answer id arrives in the
request, so a first row filed for another project, conversation or kind under
the same key is refused with 409 `proposal-card-taken` rather than returned:
a body naming somebody else's answer learns nothing of their proposal, and a
card whose position shifted never adopts a proposal of another kind.

The index is the card's position in the registry, so a card that is registered
and not taken back keeps every later card's index stable. That is why a file
operation the server did not store stays in the registry (below).

## Who may read, and who may decide

| Act | Takes | Refused with |
|---|---|---|
| Read | `project:view` on the project, and `viewer` on the conversation the proposal was made in | 404, for "missing" and "not yours" alike |
| Apply, dismiss | the read, plus the kind's right (table above) on the project | 403 (`proposal-decider-needs-write`, which names the kind); a closed project gets its own 403 |

The conversation counts because the card in that conversation is the
proposal's surface, and the payload names files, folders, notes or facts. A
reader who cannot see the conversation learns nothing from the id: a restricted
folder's audience, or a private chat.

Each item is then checked again by its own service. A decider may write the
project and still fail to move a file out of a folder they may only read; that
item fails, and its reason says why.

## How apply runs

`applyProposal` in `service.ts`:

1. Read gate, then `status === 'proposed'` (409 otherwise), then the decider
   gate for the kind. The body is optional: `{ memoryScope?: 'project' }`
   (`applyProposalRequestSchema`, strict). `memoryScope: 'project'` files an
   organization note in the project's memory instead (the card's „Nur im Projekt
   merken“). It never goes the other way, and the schema has no other value: a
   project note does not become the office's by a click on a proposal that did
   not ask for it. The other kinds ignore it.
2. **Claim**: one `UPDATE … SET applying_by, applying_since WHERE status =
   'proposed' AND (no claim, or a claim older than five minutes)`. If no row
   comes back, somebody decided or is applying it, and the caller gets a 409.
   The claim is a committed write, not a row lock, because each item's service
   takes its own connection. A transaction held across them would need a
   second pool slot while holding the first (`transaction-shape.spec.ts`).
3. **Run the kind's applier** (`applyKind`), in the deciding person's session,
   with their language for a refusal they read. For a file operation the items
   run in order, each through the service behind the Files pane's own route:

   | Verb | Resolves | Calls |
   |---|---|---|
   | `move` | the document by name on its shelf (`source`), the folder by path among that shelf's folders | `moveDocumentToFolder` |
   | `rename` | the document by name | `renameDocument` |
   | `create_folder` | the parent by path among the project's folders | `createProjectFolder` |
   | `assign` | the document by name, the person by name or email among the assignment candidates and the decider | `addResourceAssignment` |

   Names match NFC-normalized, trimmed and case-folded; among same-named rows
   the newest wins. An empty path is the shelf root. A name that no longer
   resolves, an ambiguous person, or a service refusal fails that item with a
   reason, and the remaining items still run.
4. **Settle**: one `UPDATE` that sets the final status, `results`, `decided_by`
   and `decided_at`, and clears the claim. It runs only if the claim is still
   this one. All items ok gives `applied`, none gives `failed`, and a mix gives
   `partially_applied`.

An applier separates two things. An outcome that belongs to the proposal (a name
that no longer resolves, a profile that moved) is a result. A refusal that
belongs to the decider or the moment (no right to write, a closed project, a
confined conversation) is thrown: the service gives the claim back and the
proposal stays `proposed`. The same happens if the apply breaks before it can
record anything (a stored payload that no longer parses).

A claim left by a crashed request goes stale after five minutes
(`APPLY_CLAIM_TTL_MS`), and then the proposal can be decided again. In that
case the items that already ran stay applied. Applying a file operation again
fails the `create_folder` items with "exists" and repeats the moves and renames
as no-ops. A note or a profile patch is one write, so a crash between the write
and the settle is the one case that can write it twice.

Each service does what it does for a person's click, its audit events and
inbox items included. The `task_assigned` product event, which the assignment
route sends rather than its service, is sent for an assign too.

## How decisions reach Piloti

Piloti reads what people decided about its proposals in the `PROPOSAL_DECISIONS
v1` block on the memory channel (`x-grid-project-memory`; the prompt explains
the block once, next to `PROJECT_MEMORY`). It has two sources, and a proposal is
stated once:

- **Server rows.** `listRecentDecidedProposals` reads the project's decided
  `proposed_changes`. `applied` and `partially_applied` are `angenommen` (what
  failed in a partial one is a transport fact; the line says „teilweise
  angewendet“), `dismissed` is `abgelehnt`. `proposed` is not a decision and
  `failed` is left out: nothing went through, the reader said neither, and
  Piloti may propose it again. Each line is described from the payload, what
  was applied (`Notiz`, `Profil` with the changed values, `Ablage` with the verb
  and the files), never from a card's `preview`, and is cut at 240 characters
  after masking (ADR-0086).
- **Cards without a `proposal_id`.** An answer older than server proposals, or
  one the agent could not store, keeps the browser's recorded decision
  (`cardInteractions`, ADR-0030). A card that does carry a `proposal_id` has its
  `cardInteractions` entry ignored even if a browser wrote one: the row wins.

The block rides every colleague's chat in the project, so the rows follow the
**conversation-privacy predicate** the card-decision query uses
(`conversationOpenToProjectReaders`, the same one in both). A row is read
through the conversation it was made in; it is left out when that conversation
is deleted, recorded a restricted folder, or drew on another project still
restricting its readers. A row with no origin conversation is left out too:
restricted use is recorded per conversation, so a proposal made with none has
nothing to be checked against, and failing closed costs the block a decision
while failing open could tell the office what a restricted folder holds.

## The receipt card

One card shows a proposal of any kind: `ProposalReceipt` is the frame and
`ProposalReceipts.tsx` has the three bodies (`FileOperationReceipt`,
`MemoryReceipt`, `ProfilePatchReceipt`). The three card components
(`FileOperationProposalCard`, `MemoryProposalCard`, `ProjectProfilePatchCard`)
pick it when the card has a `proposal_id`. The frame is what the kinds share and
what must not drift between them:

- It reads the proposal (`useServerProposal`) when the card is shown, after
  every decision, and when the channel says a colleague decided. It draws the
  card's own copy of the payload until the object is read, so the first paint is
  never empty and what a reader decides is what is stored.
- It offers „Übernehmen“ and „Verwerfen“ only when the server says this reader
  may decide (`canDecide`).
- Once decided it says who and when: „Übernommen von Anna · 14:02“. A
  colleague's earlier decision, a 409 or the channel's hint, becomes that
  colleague's receipt and not an error.
- A decision is a write to the proposal and nothing else. It writes no
  `cardInteractions`: a decision kept on the message would be a second truth
  beside the object. What the rest of the answer needs to know of it, the
  „Piloti hat sich gemerkt“ chip, it reads from `features/grid-cards/decided-proposals.ts`:
  `useServerProposal` records every decided object it holds (first read,
  re-read, hint, own click), and `turnMemoryItems` lists a memory card with a
  `proposal_id` only when that copy says `applied`. Cards without a
  `proposal_id` stay on `cardInteractions`.

What each body adds:

| Kind | Open | Decided |
|---|---|---|
| `file_operation` | the operation list | the same list, with each item's result and reason |
| `memory` | the note, its kind and confidence, „Ersetzt: …“ for a correction, where it goes, and for an office note a second button, „Nur im Projekt merken“ (`memoryScope: 'project'`) | „Im Gedächtnis des Büros gemerkt.“ or „Im Projekt gemerkt.“ from the result's `scope` („Notiz gemerkt.“ for a row without one), or the failure's reason |
| `project_profile` | the rationale and the Feld / Vorher / Nachher table, „Vorher“ being the profile as it is now | the table with „Nachher“ alone, because the profile holds the change by then; a failure's reason otherwise |

After a profile change is applied, by this reader or a colleague, the facts the
thread's answers bind (`:project[key]`) are told to re-read; after a file
operation the Files list is.

### Older answers, and a proposal the server did not store

A card without a `proposal_id` is one the server did not take: an answer older
than server proposals, an older BFF, a run with no envelope, or a refusal or an
unreachable route (each one `proposals.create` observation in Langfuse, with the
outcome `fallback` and its reason).

- **A file operation card** is a read-only notice. Nothing runs in the browser
  any more. A decision recorded on the message before proposals were objects is
  replayed; an undecided card says „Konnte nicht als Vorschlag angelegt werden“.
  The card is not taken back out of the registry, because that would shift the
  position of every card after it. And `propose_file_change` reports that it
  could not propose, so the model does not tell the reader a change was offered
  that nobody was shown.
- **A memory card and a profile card** keep the old browser path: the card
  decides through `useCardDecision`, writes the note or the patch from the
  reader's session, and records the decision in `cardInteractions`. That path is
  for answers that already exist, and for any run where the server cannot store
  the proposal.

## Live

A proposal is a live channel, `proposal:<id>` (ADR-0110). Being in the channel
is reading the proposal, by the rule of `GET /api/proposals/[id]`: `project:view`
on its project and `viewer` on the conversation it was made in. A reader whose
access is withdrawn is dropped at the next re-check, every 30 seconds. Nobody
writes to the channel from a browser. The service publishes one
`proposal.decided` event, with the final status, after a decision. The event is
a hint: the receipt re-reads the proposal when it arrives. A reader who misses
it finds the decision on reload, or on the 409 of their click.

## Decisions and the inbox

- **The decision score.** When a proposal is decided, one `piloti-decision`
  score goes on the trace of the turn that proposed it (the catalogue is in
  [`langfuse.md`](../observability/langfuse.md)). It is `accepted` when the
  proposal was applied or partly applied, `dismissed` when it was dismissed,
  and nothing when every item failed. It names the proposal and never the
  decider. The trace is found through the proposal's origin message; no trace
  id, no score.
- **The inbox.** A stored proposal makes `piloti.proposal_waiting` for the
  person whose turn proposed it, anchored on the proposal and pointing at the
  chat it was made in, or at the project when it had none. The line names what
  the proposal touches (`summaryOf` in `kinds.ts`: the first file names and how
  many more, a note's first words, a profile change's title). The item is
  actionable and in the app only. Whoever decides the proposal, that person or
  a colleague who may decide that kind in the project, settles it for everyone
  (`frontends/ui/src/lib/proposals/attention.ts`).
- **The audit trail.** Filing a proposal is `piloti.proposal.created` (once per
  card, as the person Piloti acted for), and deciding it `piloti.proposal.decided`
  (as the decider: how it went, the item counts, a note's memory scope), in the
  organization's WorkOS audit log; the kind and counts only, never a name or a
  word of the payload (`frontends/ui/src/lib/proposals/audit.ts`,
  [the trail](../deployment/workos-provisioning.md#5-audit-logs-native-workos-product)).
